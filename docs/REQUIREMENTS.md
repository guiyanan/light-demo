> 仓库：https://github.com/guiyanan/light-demo
> 状态：**草稿，待确认**（2026-11-04）
> 版本：v1.3 · 2026-11-05（v1.3：第 3 轮开工前用户确认——洞察输入为每篇标题 + 正文开头（接口只给前约 60 字）+ 全部保留评论，广告帖参与提炼并标注；v1.2：第 2 轮测试后用户确认——候选 40 篇按评论数挑 10 篇、每篇保留整页评论并过滤水评论；v1.1：文本模型由火山方舟改为 Kimi；v1.0：按讨论结果整体简化重写，取代 v0.x）

## 1. 背景与目标

### 1.1 背景
客户（光明乳业）希望通过小红书上的消费者内容，自动生成新品方案。本项目做一个**简单的演示 Demo**，让客户看到这条链路能够跑通，不追求生产级精度。

### 1.2 Demo 要证明的两件事
1. 能用**合规的方式**获取小红书笔记和评论（通过第三方 API 聚道云，不自建爬虫、不用小红书账号或 Cookie）。
2. 能从这些内容中提炼消费者需求，并输出**新品概念 + 包装效果图**。

### 1.3 范围
- 品类：**低温酸奶 / 发酵乳**
- 数据：搜索结果前 **40 篇**候选中评论数最多的 **10 篇**笔记（正文 + 每篇 1 页评论，去掉水评论后全部保留，最多约 100 条）
- 输出：**5 条**消费者需求 → **3 个**新品概念 → **3 张**合成展示图 → 一份可导出的报告

### 1.4 成功标准
| 编号 | 标准 |
|---|---|
| S1 | 输入 1–3 个关键词，拿到讨论最多的 10 篇笔记和它们的评论（已去掉水评论），广告帖有标注 |
| S2 | 提炼出 5 条需求，每条附 1–2 句真实原话，并注明出自正文还是评论 |
| S3 | 生成 3 个新品概念，字段完整（见 R8） |
| S4 | 每个概念 1 张合成图：左侧包装效果图，右侧程序排版的信息栏，文字与概念数据完全一致 |
| S5 | 网页上按 4 个步骤逐步点击完成，并能导出报告和图片 |
| S6 | 每次运行结果自动保存，可选择历史结果直接展示，不重新调用接口 |
| S7 | 双击 `start.command` 启动；所有单元测试在 GitHub Actions 中通过 |

### 2.3 运行方式
分工：
- **Claude 负责**：把代码 `git clone` 到 `文稿/光明demo`；从 `.env.example` 生成 `.env`（密钥留空）。
- **用户只需首次做一次**：打开 `.env`，粘贴各接口密钥并保存（Docker Desktop 已安装）。
- **用户每轮**：在访达里双击 `start.command`（内部执行 `git pull` + `docker compose up --build`），然后浏览器打开 http://localhost:8501。
`data/` 和 `logs/` 挂载到本地项目文件夹，便于直接查看日志和历史结果。

### 2.4 外部接口
| 用途 | 服务 | 已知信息 | 待确认（由 R14 接口检查确认） |
|---|---|---|---|
| 搜索笔记 | 聚道云 `GET /p6/xhs_v2/search_notes` | 参数 keyword、page、sort_type 等；Bearer 鉴权；402 = 额度不足 | 返回数据结构；是否有"广告"标识字段 |
| 笔记评论 | 聚道云 `GET /p6/xhs_v2/get_note_comments` | 参数 note_id、cursor、sort_strategy | 返回数据结构；每页条数 |
| 文本模型 | Kimi 开放平台 API（月之暗面，platform.moonshot.cn） | OpenAI 兼容；Base URL、模型 ID 可配置；**须用开放平台的 API Key，Kimi Code 会员的 Key 是另一套，不能混用** | 具体模型 ID（如 kimi-k3） |
| 生图 | BananaRouter，模型 `gpt-image-2` | OpenAI 兼容 `POST /v1/images/generations`；返回 `b64_json` 或 `url` | Base URL、模型名写法、同步还是异步 |

## 3. 功能需求

> 每条需求的验收标准都必须能被单元测试验证（外部接口一律模拟）。

### 3.1 基础
| 编号 | 描述 | 验收标准 |
|---|---|---|
| R1 | 配置加载：密钥和地址从 `.env` 读，业务参数从 `config/app.yaml` 读 | 缺必填项时报错并指出缺哪个字段；日志里密钥只显示前 4 位 |
| R2 | 结构化日志：JSON 格式，分 app / error / test / build / diag 目录；每个流程步骤记录开始、结束、条数、耗时；外部调用记录方法、URL（不含密钥）、状态码、耗时 | 每条日志含 timestamp、level、module、message、request_id、status_code、error_type、stack；测试断言日志中不出现密钥原文 |
| R3 | 外部调用容错：401/402/400 不重试，直接报错；429/5xx 指数退避，最多重试 3 次（生图最多 2 次）；超时可配置 | 用模拟状态码验证重试次数、错误类型和日志 |

### 3.2 数据抓取
| 编号 | 描述 | 验收标准 |
|---|---|---|
| R4 | 搜索笔记：按关键词（1–3 个）取搜索结果**前 40 篇候选**（多关键词时按顺序轮流取、按 note_id 去重，凑满 40 篇或无更多结果为止）；从候选中去掉评论数 **< 3** 的笔记，按评论数从多到少挑 **10 篇**（评论数相同保持搜索顺序）；不足 10 篇时如实展示实际篇数 | 关键词为 0 个或超过 3 个时报错；分页终止条件、去重；按评论数挑选、门槛与平局规则；字段标准化为 `note_id, keyword, rank, search_rank, title, desc, liked, collected, comments, tags, is_ad` |
| R5 | 广告标注：广告帖保留，`is_ad=true`，页面显示"广告"标签 | 用含广告标识的模拟数据验证；接口没有广告字段时 `is_ad=false` 并记日志 |
| R6 | 评论：每篇笔记取 1 页评论（约 10 条），**去掉水评论后全部保留**，按点赞从高到低排列。水评论：去掉表情代码后少于 3 个字、只有话题标签 / 商品标签、或含引流 / 代购类词（如 pm、代购、建联、私信、互关）；提问和吐槽（如「热量多少」「哪里买」「太酸了」）保留 | 每篇 ≤1 页、按点赞排序；水评论被过滤并计数、正常短评保留；字段 `comment_id, note_id, content, likes` |
| R7 | 隐私：不保存用户昵称、用户 ID、头像、IP 属地 | 标准化结果和导出物中不含这些字段（测试断言） |

### 3.3 需求洞察
| 编号 | 描述 | 验收标准 |
|---|---|---|
| R8a | 调用大模型，从本次抓取的每篇笔记**标题 + 正文开头**（搜索接口只给前约 60 字）+ **全部保留的评论**中提炼 **5 条**消费者需求。**广告帖参与提炼**（代表竞品在主推什么），输入中标明是广告帖。每条需求包含：标题、一句话描述、类型（正面 / 负面 / 期待）、1–2 条原话证据（含来源：正文或评论、note_id，以及是否出自广告帖） | 输出用 JSON Schema 校验，不合格重试 1 次，仍失败则在页面报错；按输入内容哈希缓存，同样的输入不重复调用；输入中广告帖带标记；出自广告帖的原话在页面标注「广告帖」 |
| R8b | 原话真实性：每条原话必须是对应来源原文的子串（来源为正文时，标题或正文开头均可） | 非子串的原话被丢弃并计数；某条需求丢光原话时整体重试 1 次，仍不合格则标注"缺少证据" |

### 3.4 新品概念
| 编号 | 描述 | 验收标准 |
|---|---|---|
| R9 | 根据 5 条需求生成 **3 个**新品概念。每个包含：品名、一句话卖点、目标人群、主要原料（列表）、包装形式、规格、每 100g 营养估算（蛋白质、碳水/糖、脂肪、热量）、对应的需求编号、生图提示词 | JSON Schema 校验；营养数值字段固定标注"AI 估算"；引用的需求编号必须在 1–5 之内 |

### 3.5 产品图
| 编号 | 描述 | 验收标准 |
|---|---|---|
| R10 | 生图：通过 BananaRouter 调用 `gpt-image-2` 生成包装效果图（默认 1024×1024，可配置）；提示词要求**包装上不出现任何文字和 logo**；超时默认 180 秒 | 模拟测试覆盖：返回 b64_json、返回 url、超时、400 不重试、5xx 重试；提示词中包含"无文字、无 logo"约束 |
| R11 | 合成展示图：Pillow 合成 1600×1000 PNG。左侧为效果图；右侧信息栏：顶部品名 + 一句话卖点，下方目标人群、主要原料、包装形式与规格、营养估算（标"AI 估算"）；右下角小字"AI 概念图 · 非最终设计"；左上角预留 logo 空位（暂不显示内容） | 图上所有文字都来自概念数据（测试断言渲染文本与数据一致）；中文字体可用；生图失败时左侧使用灰色占位图，信息栏照常生成 |
| R12 | 品牌元素：程序不生成、不仿制光明 logo；客户提供 logo 文件后再放到 `assets/logo/` 并贴到预留位置 | 不调用生图模型画 logo |

### 3.6 网页、导出与运维
| 编号 | 描述 | 验收标准 |
|---|---|---|
| R13 | 网页按 4 步逐步点击：①数据抓取 ②需求洞察 ③新品概念 ④产品图与导出；每步一个按钮，不提供"一键跑完"。另有"接口检查"页 | 业务逻辑都在 `pipeline/` 中并有单元测试，界面只负责调用和展示；某步失败时显示错误摘要和 request_id，并提供"重试这一步"按钮，不影响已完成的步骤 |
| R14 | 接口检查：网页"接口检查"页和命令 `python -m app.diag` 依次测试聚道云、Kimi、生图，显示成功 / 失败、状态码、耗时；脱敏后的原始响应存到 `logs/diag/` | 模拟测试成功和失败路径；输出中不含密钥 |
| R15 | 运行记录：每次运行保存到 `data/runs/<run_id>/`（原始响应、笔记、评论、需求、概念、图片、调用次数）；网页可选择历史运行直接展示 | 保存后能完整读回并展示，不触发任何接口调用（测试断言调用次数为 0） |
| R16 | 导出：一份 HTML 报告（含需求及原话、3 个概念、3 张图，广告帖有标注，可打印为 PDF）+ 3 张 PNG 的 zip | 导出文件包含全部字段；不含用户身份信息 |
| R17 | 部署：Docker 镜像内装中文字体；`.env` 通过 compose 注入；`data/`、`logs/` 挂载到宿主机；`start.command` 执行 `git pull` 和 `docker compose up --build` | CI 中 `docker compose build` 成功 |

## 4. 非功能需求
| 类别 | 要求 |
|---|---|
| 性能 | 单次全流程目标 ≤ 5 分钟（取决于接口速度，不作为测试项）；聚道云调用约 12–20 次（每次约 240–400 点） |
| 安全 | 密钥只在 `.env`；`.env`、`logs/`、`data/runs/` 不提交；日志和接口检查输出都打码 |
| 隐私 | 不保存小红书用户身份信息；导出物中只有原话，没有作者 |
| 可替换性 | 大模型和生图的 Base URL、模型 ID 可配置，换供应商不改代码 |
| 测试 | 不依赖网络、随机数、当前时间和执行顺序 |
| 日志 | 所有功能都有日志；出错时先在出错位置稳定复现，再修复 |

## 5. 本期不做
- 自建爬虫、使用小红书账号或 Cookie；接入 RedFox、抖音、电商等其他数据源
- 热度排名公式（直接使用搜索结果的前 10 篇）
- 内部参数 Excel、成本估算、产线可行性校验
- 合规校验（由客户法务等部门负责）
- 精确配方和工艺参数；营养数字仅为 AI 估算
- 生成或仿制 logo；包装平面展开图、印刷稿
- "一键跑完"、多人协作、登录权限、生产级部署
